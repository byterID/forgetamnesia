# SPEC — синхронизация через Google Drive (M2)

ADR-003, 004, 014. Цель: **ни при каком сценарии не потерять подтверждённые пользователем данные**.

## S1. Модель
- Источник правды на устройстве — Dexie. UI пишет только через репозитории, каждая запись порождает `Op` в той же транзакции Dexie.
- `Op = { id: uuidv7, deviceId, seq: number, hlc: string, schema: number, entity, entityId, kind: 'put'|'patch'|'delete', fields?: Record<string, unknown> }`.
- `seq` — монотонный счётчик устройства, без пропусков.
- **HLC** (`<physicalMs>-<counter>-<deviceId>`): при получении чужих операций часы продвигаются до max. Защищает от расхождения часов устройств.
- Слияние: для каждого поля сущности побеждает операция с наибольшим `(hlc, deviceId)`. `delete` — tombstone (`deletedAt`), поздний `put` после delete **не воскрешает** без явного restore-op.
- Применение операций идемпотентно (повторное применение не меняет результат).

## S2. Файлы в `appDataFolder` (scope `drive.appdata`)
```
manifest.json                       { formatVersion, accountSub, createdAt }
ops-<deviceId>-<firstSeq>.jsonl     чанк журнала, до 500 операций; пишет ТОЛЬКО владелец
snapshot-<hlc>-<deviceId>.json      полное состояние + vector { deviceId: lastSeq }
devices.json  → НЕ используем (общий изменяемый файл = гонки); список устройств выводится из имён чанков
```
Каждый файл — в **конверте** `{ v: 1, enc: 'none' | 'aes-gcm', iv?, payload }`.
Drive не умеет append → текущий (незаполненный) чанк перезаписывается целиком; это безопасно, т.к. пишет только владелец.
`appProperties` файла: `deviceId`, `firstSeq`, `lastSeq` — чтобы не скачивать файл ради метаданных.

## S3. Цикл синхронизации
Триггеры (никакого опроса раз в секунду):
- старт приложения; `visibilitychange → visible`; событие `online`;
- после локальной записи — debounce 3 с;
- пока вкладка видима — страховочный тик раз в 5 мин;
- ручная кнопка «Синхронизировать».

Шаги:
1. **Захватить блокировку** `navigator.locks.request('fa-sync')` — синхронизирует ровно одна вкладка; остальные получают изменения через `BroadcastChannel` + liveQuery.
2. **Pull**: `changes.list(spaces=appDataFolder, pageToken)` → какие чужие чанки/снимки изменились. Скачать только операции с `seq > known[deviceId]`.
3. Применить чужие операции в одной Dexie-транзакции, обновить HLC и `known`.
4. **Push**: свои неотправленные операции → дописать в текущий чанк (перезапись) или создать новый. После успеха — пометить `pushedSeq`.
5. Сохранить новый `pageToken`.
Если в шаге 2 обнаружен **пропуск seq** у другого устройства — не применять дальше пропуска, повторить позже (чанк ещё заливается).

## S4. Снимки и компактирование
- Снимок создаётся, если с прошлого суммарно > 2000 операций или раз в 7 дней. Хранить 3 последних снимка.
- Новое устройство: скачать последний снимок → затем операции с `seq > vector[deviceId]`.
- Чанк удаляет **только его владелец** и только если он полностью покрыт снимком, которому > 30 дней.

## S5. Угрозы и защита (каждая — тест или явная проверка)
| # | Угроза | Защита |
|---|---|---|
| 1 | Два устройства пишут один файл | Каждый пишет только свои чанки. Снимки — уникальные имена. |
| 2 | Две вкладки одного устройства синхронизируют одновременно | Web Locks API + BroadcastChannel. |
| 3 | Обрыв сети / закрытие посреди загрузки | `pushedSeq` двигается только после ответа 200; повтор идемпотентен; загрузка — resumable/multipart целиком. |
| 4 | Истёк токен посреди цикла | Перехват 401 → тихое обновление → повтор шага; если нужно окно входа — пауза, баннер, данные остаются локально. |
| 5 | 403 rateLimit / 429 / 5xx | Экспоненциальный backoff с джиттером, максимум 5 попыток, затем следующий триггер. |
| 6 | Drive переполнен (`storageQuotaExceeded`) | Баннер; локальная работа продолжается; не терять очередь. |
| 7 | Расхождение часов устройств | HLC. |
| 8 | Разные версии приложения на устройствах | `Op.schema`; неизвестные поля/сущности **сохраняются**, не отбрасываются; баннер «обнови приложение»; формат файлов — `manifest.formatVersion`. |
| 9 | Браузер вычистил IndexedDB | `navigator.storage.persist()` при первом запуске; при пустой базе + существующих данных в Drive — восстановление из снимка; новый `deviceId`. |
| 10 | iOS Safari удаляет данные неустановленного сайта через 7 дней | Подсказка «Установить на экран Домой»; синхронизация как бэкап. |
| 11 | Вход другим Google-аккаунтом | `manifest.accountSub` ≠ локальному → не смешивать, спросить пользователя. |
| 12 | Пользователь удалил скрытые данные приложения в настройках Drive | Пустой `appDataFolder` при непустой локальной базе → спросить «Загрузить данные этого устройства заново?». |
| 13 | Повреждённый/недокачанный файл | Проверка JSON + `lastSeq` из `appProperties`; повреждённый чанк — пропустить и повторить; снимок — откат к предыдущему. |
| 14 | Воскрешение удалённого | Tombstone-правило из S1. |
| 15 | Локальный бэкап на случай проблем с Google | Экспорт/импорт полного JSON в настройках (M3). |

## S6. UI синхронизации
Иконка в шапке: ✓ синхронизировано (время) · ⟳ идёт · ⚠ ошибка (тап → причина и действие) · ⊘ офлайн / не подключено.
Никаких блокирующих спиннеров: пользователь всегда может работать.

## S7. Тестирование
- Юнит: HLC, слияние (свойство: порядок применения не важен — property-based через fast-check), tombstones.
- Интеграция: фейковый Drive-адаптер в памяти, 3 «устройства», случайные операции и обрывы — состояния сходятся.
- Ручная проверка на тестовом Google-аккаунте: два браузерных профиля + телефон.
